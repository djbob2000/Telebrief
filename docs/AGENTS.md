# AGENTS.md — архитектурная документация Telebrief

Инструкции для агентов, которые редактируют архитектурную документацию в `docs/`. Описание для людей — в `README.md`.

## Когда обновлять

Документация описывает текущее поведение кода, поэтому меняется в том же изменении, что и архитектура (правило из корневого `AGENTS.md`). Обнови её, если изменение:

- добавляет, удаляет или переименовывает компонент, процесс Compose, очередь, задачу Procrastinate или периодическое расписание;
- меняет порядок шагов сценария, машину состояний, условия готовности, повтора или отказа выпуска;
- меняет таблицы, ключи уникальности, внешние сервисы, модели или их назначение;
- меняет константу, лимит, таймаут или код ошибки, записанные в разделе L3;
- принимает или отменяет решение, которое кто-то может оспорить, — тогда новый ADR или статус «Заменено» у старого;
- открывает или закрывает известный риск — раздел `l3-risks`.

Где менять — по правилу «один факт — одно место» ниже. После правки — `npm run build`.

## Главное правило

`index.html` **сгенерирован**. Не редактируй его вручную — правки пропадут при следующей сборке.
Источник — `architecture/`. После любого изменения в `architecture/` запусти из папки `docs/`:

```sh
npm run build   # собирает index.html из architecture/ и проверяет ссылки; должно закончиться "check: OK"
```

Коммитим и `architecture/`, и собранный `index.html`.

## Где что лежит

| Путь (от `docs/`) | Что это |
| --- | --- |
| `architecture/l1/`, `l2/`, `l3/`, `ops/`, `adr/` | один раздел = один `.md`; порядок — по префиксу имени (`03-components.md`) |
| `architecture/_shell.html` | шапка, боковая панель, слайд-шоу, скрипты; места вставки `{{nav}}`, `{{sections}}`, `{{aliases}}` |
| `architecture/aliases.json` | старые якоря слитых разделов → новые |
| `tools/build.mjs` | сборка `architecture/` → `index.html` |
| `tools/check.mjs` | проверка внутренних якорей и пустых mermaid-блоков |
| `assets/docs.js`, `assets/docs.css`, `serve.js` | движок страницы, комментарии, сервер |
| `comments.json` | комментарии рецензентов; не редактировать без нужды |

Остальное в `docs/` (`operations/`, `plans/`, `superpowers/` и др.) — отдельные документы, сборка их не трогает.

## Формат раздела

```markdown
---
id: "l2-digest"                         # якорь раздела, уникальный, обязательно
level: "L2"                             # L1 | L2 | L3 | OPS | ADR, обязательно
eyebrow: "Уровень 2 · Сценарий 2"       # подпись над заголовком
nav: "Сценарий 2: Ежедневный дайджест"  # пункт меню (без nav раздела нет в меню)
group: "Выпуск"                         # только L3: группа в меню
---

## Заголовок раздела

Текст…
```

- Обычный Markdown + таблицы GFM.
- Диаграммы — блок ` ```mermaid `. В сообщениях `sequenceDiagram` не используй `;` — диаграмма молча не отрисуется.
- Блок «Коротко» — `::: tldr` … `:::`.
- id заголовка — `### Заголовок {#l1-names}`.
- Сырой HTML разрешён там, где не хватает Markdown (SVG-схемы, карточки, сложные таблицы, `p.adr-meta`). **Внутри HTML-блока не должно быть пустых строк** — иначе Markdown оборвёт блок. Таблицу в `<div class="tw">` отделяй пустыми строками от тегов.
- Новый раздел: создай `.md` со следующим номером в нужной папке; пункт меню появится сам. Переименовываешь или сливаешь раздел — добавь старый id в `architecture/aliases.json`.

## Комментарии — не сломай

`assets/docs.js` привязывает комментарии из `comments.json` к разделу (`sectionId`) и блоку: по порядковому номеру блока и первым 80 символам его текста, текстовые комментарии — по точной цитате.
Поэтому:
- не меняй `id` разделов;
- не переписывай без нужды текст блоков, к которым есть комментарии;
- после правок открой страницу и убедись, что в панели комментариев нет пометки «фрагмент не найден».

## Проверка

1. `npm run build` — `check: OK`.
2. `npm run serve` (или `node serve.js`) → http://localhost:8766/: раздел открывается из меню, mermaid-диаграммы отрисовываются, комментарии на месте.

## Содержание документации

- Уровни и аудитория: L1 — простым языком для менеджеров, без путей, констант и названий моделей; L2 — сценарии с упрощёнными диаграммами; L3 — технические детали с файлами и константами; ADR — «почему так» в формате MADR (статус, дата, варианты); ADR не удаляют, а помечают «Заменено».
- Каждый факт записан в одном месте, остальное — ссылки: числа и коды ошибок → L3, порядок шагов → L2, обоснование → ADR, процедуры → OPS (указатель на `docs/operations/`).
- Описывается текущее поведение кода. Если код расходится с корневым `AGENTS.md`, документируй код и запиши расхождение в раздел `l3-risks`. Непроверенное помечай «Needs verification».
- Источник фактов — код в `src/`, `migrations/`, `config.yaml`; пути в тексте пиши от корня репозитория (`src/jobs/schedules.py`). Не указывай в документации секреты, адреса серверов, имена ботов и личные данные.
