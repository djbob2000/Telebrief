# Проверка редакционного качества дайджеста

План: `docs/superpowers/plans/2026-10-04-readable-city-digest.md`.
Снимки synthetic-v1 созданы до настройки нового writer/editor; live source prose в Git не сохраняется.

Development: rich_utilities, quiet_day, local_contrasts, practical_services.
Holdout: partial_announcements, community_microdetails. Не использовать holdout для настройки prompts.

Критерии: 100% выбранных Stories/facts; honest single-source attribution; неизменные цитаты; лимит Telegram; no fallback. Editorial score: пять измерений 0–4 (hierarchy, cohesion, repetition, usefulness, detail/attribution), сумма ×5. Оценки выставляются по готовому тексту с примерами; отсутствующие source details не дописываются.

Synthetic cases используют один общий тестовый блок, чтобы сравнивать синтез независимо от Selection/rubric assignment. Этот набор не заменяет реальные multi-rubric снимки и не подтверждает production rollout сам по себе.

Baseline и новые варианты выполняются через offline replay, без базы и доставки. Отчёты/тексты: `data/previews/digest-evaluation/` (ignored). Отказы учитываются вместе с успешными результатами.

Статус: сравнение завершено; rollout отклонён по редакционным и эксплуатационным критериям.

Synthetic scores: пять измерений 0–4, сумма ×5. Нельзя интерпретировать 100/100 короткого искусственного примера как идеальность реального продукта. На реальном выпуске каждый из шести текстов получил [3,2,2,3,4]: тематическая иерархия присутствует, но связность и повторы слабы; фактура сохранена, практическая польза ограничена доступными сведениями.

Примеры нерешённых дефектов: «в районе РТС ... нет электричества уже неделю» и следом «свет ... так и не дали» повторяют одну мысль; «Отдельное сообщение указывает» заменяет рассказ о городе рассказом об источнике; «АКЗ: сообщения ... расходятся» дублируется в теле. В synthetic holdout несколько пунктов одинаково начинались «По местному сообщению», а поздняя атрибуция «...; по местному сообщению» нарушала плавность фразы. Эти дефекты не объявлены фактическими блокерами.

Технически все принятые кандидаты имели 100% metadata Story/material-fact coverage и укладывались в один Telegram пост. Семантические binding checks частично `not_evaluated`: техническое принятие не доказывает полноту литературной или смысловой оценки. В одном раннем кандидате редактор придумал «в другом доме» без места в источниках; добавлен узкий safety regression check с контролем, который сохраняет такую формулировку, когда она явно есть в единственном источнике.

Снимок run 306 реконструирован из sealed publication inputs и source revisions в `REPEATABLE READ READ ONLY` транзакции. Это реконструкция, не доказательство точного совпадения со всем контекстом оригинального запуска. После экспорта replay не читает БД. Снимок содержит 18 Stories и четыре рубрики; SHA256 экспортированного JSON: `7f1c82366c4d84b9427d32ada6adad471c4118f3197fac1a2efa2f1cc89d18ca`. City profile на сервере и локально совпал: `8f98735cf79b6501b5f76e7c879f7611ae548ade825fec12396d0fcd0850a503`. Новые replays требуют hash географического профиля и прекращаются до provider call при его изменении. Версия модели разрешалась из имеющейся конфигурации и записывалась в каждом результате; provider availability не гарантируется снимком.

Synthetic holdout использован для итогового сравнения. После анализа его регрессий дальнейшие варианты не получают статус проверки на независимом holdout; для следующего допуска нужен новый заранее закрытый набор реальных окон. Промпт thematic-v3 исправлялся по реальному development run 306; его результаты не заменяют повторный holdout.

## Решение

`digest_writer_material_format=legacy` и `digest_editor_scope=targeted_items` остаются production defaults. Новый компактный материал и полный тематический scope доступны для дальнейших offline сравнений. Обязательная AI-редактура без замечаний доступна только экспериментальным CLI флагом. Подмена готового текста технической склейкой не добавлена, фактические проверки не ослаблены, подтверждение из двух источников не требуется.

Активация, деплой нового режима и просмотр первых трёх штатных выпусков не выполнены: acceptance criteria не достигнуты. Следующая работа — на новых реальных снимках отделить ограничения writer/editor от ограничений состава плана, проверить источник повторяющихся фактов и неясных контекстных пунктов до планового утверждения, а затем повторить сравнение. Удалять утверждённые факты из готового текста ради хорошего балла нельзя.

## Продолжение проверки 05.10.2026

На тех же sealed-окнах 297, 306 и 309 сделаны дополнительные offline full-pipeline replay через writer, editor и assessment; использовалась прежняя модель `openai/gpt-6-luna`. Это development-набор, не новый независимый holdout. В production ничего не доставлялось; база не читалась и не изменялась.

Диагностика нашла две ошибки маршрутизации: `water_supply` не попадал в распознавание основной коммунальной темы, а русские формы «электричества» не всегда относились к электроснабжению. Они исправлены в классификации для presentation grouping. Компактный writer-input теперь не получает массовые попарные `RELATED_ONLY` связи; все fact/support/unit IDs сохраняются. `related_reporting_sets` дополнен навигацией по фактам, извлечённым из одного и того же support. Writer/editor явно инструктируются считать ID списком покрытия, а не требованием писать отдельное предложение на каждый ID. Эти навигационные изменения не удаляют и не объединяют доказательства.

Дополнительно исправляется очевидное согласование числа в атрибуции, например «жители сообщает», только вне кавычек; прямая цитата остаётся неизменной. Классификатор выдаёт для такой ошибки необязательное замечание, но редактор на этих окнах несколько раз возвращал некорректную структурную переработку. Исправление согласования поэтому выполняется локальным детерминированным преобразованием до assessment.

На последнем варианте `compact_v1 + thematic_blocks` 8 из 9 генераций получили `accepted`; один запуск run 306 завершился до assessed draft с `ValueError`. У всех 8 принятых текстов metadata Story/fact coverage составил 100%; длина — 1 626–2 205 UTF-16 единиц. При этом по-прежнему остаются повторы условий, перечисление коротких сообщений и слабая связность части абзацев. Часть editor-переработок была отклонена строгим контролем фактов из-за пропущенных или повторённых ID; сохранялся предыдущий checkpoint. `accepted` здесь подтверждает safety/coverage, а не литературное качество. Редакционная оценка последних кандидатов исполнителем — ориентировочно 55–75/100, медиана на глаз около 60–65; независимое слепое ревью не проводилось.

После удаления ложных текстовых якорей, созданных заглавными словами вроде «НЕТ» и «СВЕТА», один целевой replay run 306 был принят с 100% Story/fact coverage, 1 720 UTF-16 единицами и без style warnings. Это один случай, а не подтверждённая оценка устойчивости. В тексте РТС уже сведены в один связный пункт с диспетчерской версией причины; остальные районы сохранены раздельно, где их нельзя безопасно объединить.

Вывод: маршрутизация темы, source-overlap подсказки и грамматическая чистка улучшены, но это не решило главную проблему читательского текста устойчиво. Компактный writer и широкая тематическая редактура не включаются по умолчанию: production defaults остаются `legacy` и `targeted_items`. Следующий эксперимент — на новом заранее закрытом наборе сравнить плоский список обязательных фактов с группировкой исходных материалов и связанными с ними fact IDs. Сравнение должно показать, станет ли сама задача writer проще и уменьшатся ли дубли без потери выбранных Stories или RequiredDigestFacts. До этого rollout по критерию качества не разрешён.

### Source-first вход, 05.10.2026

На тех же development-окнах 297, 306 и 309 проведено девять полных offline replay варианта `source_grouped_v1` (по три повтора на окно), с writer, editor и assessment. Этот вход группирует исходные фрагменты вокруг связанных Stories/supports и оставляет fact IDs для проверки покрытия. Плоский контракт результата и детерминированная проверка покрытия не менялись.

Все 9/9 replay получили `accepted`, 100% metadata Story/fact coverage и уложились в лимит одного сообщения (1 541–2 139 UTF-16 единиц). Это не дало заметного преимущества перед предыдущим compact-набором: на тех же окнах его 9/9 replay также были приняты с 100% metadata coverage. Число provider calls осталось сопоставимым. При этом тексты source-first не стали устойчиво более журналистскими: несколько вариантов снова следовали за группами входных данных почти по одной на пункт, перегружали заголовки рубрик и повторяли атрибуцию или содержание. В других повторах группировка давала более крупные абзацы, но повторы фактов и слабые переходы сохранялись. Ручная редакторская оценка автора эксперимента — примерно 55–70/100; независимого слепого ревью нет.

Вывод: группировка источников полезна как контекстная навигация, но сама по себе не решает проблему композиции иерархичного дайджеста. `source_grouped_v1` остаётся только offline-экспериментом; production defaults и поведение публикации не меняются. Не следует считать 9/9 технически принятых текстов доказательством редакторского улучшения. Следующее сравнение должно на заранее закрытых реальных окнах проверять более простой авторский бриф: предоставить модели цельный отобранный корпус фактов и попросить написать связный дайджест с широкой тематической иерархией, а IDs использовать только для последующей детерминированной проверки покрытия, не как единицы композиции. Нужны слепое сравнение текстов с текущим вариантом и оценка числа потерь/добавлений фактов; prompt tuning на holdout запрещён.

### Цельный корпус и свободная композиция, 05.10.2026

Проверены две версии offline writer probe на новых снимках из серверной базы. Снимки run 307, 294 и 253 использовались для настройки (development); для версии 2 заранее выбраны другие окна run 214, 187 и 164 (holdout). Снимки восстановлены из sealed publication inputs в `REPEATABLE READ READ ONLY`; после экспорта replay базу не читает. Во всех генерациях использовалась `openai/gpt-6-luna`; production и база не изменялись. Тексты и снимки лежат во временной папке `/tmp/telebrief-digest-new-sealed/`.

Вариант 1 передавал модели цельный корпус выбранных свидетельств и короткий бриф, без fact IDs и схемы композиции. Текст получался связным, но на первом holdout окне 248 оказался слишком коротким и опускал выбранные темы. После этого пример использовался только для диагностики и не включён в следующий контроль. На development окнах бриф уточнили: сохранить каждую уникальную тему и деталь, объединять только повторяющиеся сведения, не добавлять неподтверждённых оговорок. Затем формулировка была зафиксирована.

Для версии 2 получено по три черновика на каждом из трёх development и трёх новых holdout окон; все 18 вызовов вернули текст. Длина development черновиков — 1 592–2 107 знаков, holdout — 1 985–2 514. Сохранённые публикации на трёх holdout окнах содержат 3 442, 4 114 и 9 895 знаков. По просмотру примеров версия 2 чаще объединяет темы в связные абзацы и сокращает повторы и общий объём. Независимого слепого редакторского ревью не было.

Свободная композиция пока не допускается к публикации: утверждения не размечались обратно на источники, поэтому пропуски и добавления версии 2 не измерены. В development черновике версии 1 модель привязала «60–80 вольт» к Собачьей балке, хотя место в исходном факте не указано. Версия 2 также включает второстепенный контекст из чатов. Наличие всех деталей в тексте нужно проверить отдельно от его связности.

Параллельные full-pipeline сравнения с лимитом writer 32 768 токенов получили 402 от OpenRouter (`in_flight_budget_exhausted`); повторные попытки не являются валидными сравнениями. После снижения лимита до 4 096 и последовательных вызовов свободный probe завершился. Неудачные попытки в результаты не включены.

Решение: свободный текст перспективен как черновик, но до допуска ему нужна привязка утверждений к свидетельствам. Следующий offline spike — взять сохранённые черновики версии 2 и поручить отдельному связующему проходу вернуть для предложений только IDs `RequiredDigestFact` и `PUBLISH` supports, не меняя текст. Затем код должен посчитать непокрытые факты и утверждения без привязки, отдельно проверить места, числа, сроки, причины и цитаты. Результат сверить вручную с источниками. Если связность сохраняется, а пропуски и неподдержанные добавления удаётся обнаружить, можно спроектировать text-first pipeline. До этого production defaults не меняются.

#### Результат связующего прохода

На сохранённых черновиках проверен offline binder: он возвращает точные текстовые диапазоны абзацев, связанные `RequiredDigestFact`/support IDs, список пропущенных фактов и точные неподдержанные фрагменты; текст он не редактирует. На двух черновиках версии 2 (development run 307 и holdout run 187) binder нашёл соответственно 10 и 7 непокрытых обязательных фактов, а также 9 и 11 фрагментов, требующих проверки. Все возвращённые диапазоны совпали с подстроками исходного черновика; неизвестных fact/support IDs не было. На диагностическом черновике run 294 binder отметил «На Собачьей балке» как неподдержанную локацию — это совпадает с известным дефектом: источник сообщал напряжение 60–80 В, но не называл эту локацию.

Этот результат подтверждает, что binder способен направить редакторскую проверку на рискованные места и измерить часть пропусков. Он не подтверждает сам себя: на тех же примерах он также пометил некоторые даты и осторожные оговорки как неподдержанные, а почти все абзацы получил статус `partially_supported`. Известный дефект был обнаружен как неподдержанная часть абзаца, но не перевёл абзац в статус `unsupported`. Поэтому выводы модели binder нельзя считать доказательством или автоматическим основанием для публикации/отказа; нужна детерминированная проверка точных диапазонов и ID плюс проверка решения редактором по первоисточнику.

Решение: свободный writer остаётся только генератором черновика. Binder — перспективный диагностический слой, но не публикационный шлюз. Следующий эксперимент должен проверить замкнутый цикл на новом заранее закрытом наборе: binder указывает конкретные непокрытые факты и неподдержанные диапазоны, ограниченная редакторская правка исправляет только эти места, затем текст повторно связывается с источниками и проходит текущие фактические инварианты. Сравнивать надо итоговые тексты, полный список пропусков/добавлений и стоимость/отказы с текущим пайплайном. До успешного ручного аудита на holdout и достижения 100% покрытия без неподдержанных утверждений production defaults не менять.

#### Проба ограниченного ремонта

Сделан один repair pass на development run 307, затем тот же замороженный бриф применён к holdout run 187. Редактор получал непокрытые fact IDs, отмеченные абзацы/точные фрагменты и первоисточники соответствующих фактов; он мог вернуть полный связный текст, но должен был исправлять только указанные места. После ремонта тот же binder проверил текст повторно. Количество замечаний binder сократилось: на run 307 пропуски 10→2, подозрительные фрагменты 9→3; на run 187 — 7→4 и 11→3. Тексты выросли с 1 867 до 2 157 знаков и с 2 514 до 2 437 знаков соответственно; обе версии остались ниже лимита Telegram. Диапазоны абзацев оставались точными подстроками, неизвестных ID не появилось.

Это предварительный хороший сигнал, но не принятие решения о качестве: на development всё ещё остались два пропуска и как минимум один серьёзный географический фрагмент про «третий пляж»; на holdout — четыре пропуска. Binder также пометил на holdout общие связки вроде «главная городская тема» и «на фоне перебоев», что подтверждает его склонность к ложным тревогам. Во всех текстах нужны ручная проверка оставшихся claims и редакторская оценка связности; автоматическое повторение repair pass пока не проверялось и может зациклиться или добавить новые ошибки.

Уточнение после проверки самого инструмента: первый binder не передавал `observed_at` и `reply_parent_context_text`, хотя оба поля есть в sealed-снимках. Это могло вызывать ложные замечания к датам и репликам. После добавления этих полей как отдельной временной метки и контекста (не прямого текста источника) повторная проверка отремонтированных текстов run 307 и 187 вернула 2 и 4 непокрытых ID, 1 и 2 подозрительных фрагмента соответственно. В run 307 список пропусков содержал один неизвестный fact ID — кодовый smoke-check поймал его через `uncovered_ids_known=false`; значения из такого результата нельзя считать точным покрытием. На holdout остались четыре известных RequiredDigestFacts без покрытия. Значит, для любого будущего binder-контракта нужно проверять принадлежность ID плану и в claim mapping, и в списке непокрытых фактов; включение полного контекста улучшает диагностику, но не устраняет ошибки самой модели.

Вывод: ограниченный repair pass заметно сокращает диагностический остаток на одном проходе и стоит проверки как этап offline-эксперимента. Следующая итерация должна сверить каждое оставшееся замечание и каждый пропущенный факт с источником вручную, отдельно оценить, не ухудшил ли ремонт композицию, и только затем решить, оправдан ли второй bounded pass. На данном результате внедрять цикл в production рано; текущие defaults и правила публикации не меняются.

### Ручной аудит привязки фактов, 06.10.2026

Сверка оставшихся binder findings с `RequiredDigestFact`, `PublicationEvidence`, первичным текстом и `reply_parent_context_text` выявила первичный дефект выше уровня digest writer. В run 307 карточка о трёх сутках без света в центре (`story:37965`) ссылается на ответ с исходным текстом «На 3 пляже его уже нету третий месяц». Контекст родителя содержит отдельное сообщение о центре и трёх сутках, а первичное сообщение родителя присутствует как самостоятельное `PUBLISH`-свидетельство в `story:37940`. Следовательно, факт центрального отключения оказался приписан дочернему ответу; сообщение про третий пляж — отдельная деталь, которую нельзя превращать в центр/три дня.

Похожая ошибка в run 187: карточка о том, что вода появляется только при электричестве (`story:17557`), ссылается на ответ «А по свету ничего не известно», тогда как соответствующее высказывание находится в контексте родителя и отдельно представлено сообщением `story:17545`. В `story:17482` утверждение о звонке в водоканал и полном отключении взято из контекста родительской реплики, но PUBLISH-support указывает на саркастический ответ «Работа у них такая! Без паники скучно!». Без самого родительского сообщения это не support для обязательного факта об отключении.

Это не повод глобально запрещать публикацию ответов или контекстно-зависимых сообщений. Требуется сохранять владельца утверждения: прямой фрагмент может пояснять родительскую тему, но факт родителя должен ссылаться на собственный PUBLISH-support; если такой support отсутствует в sealed material, факт нельзя выдавать за подтверждённое содержание ответа. Следует устранять ошибочную source-fragment привязку в Event-First extraction/normalization и проверять соответствие fact → exact PUBLISH support до формирования `RequiredDigestFact`.

Проверка других запечатанных окон показывает, что это не единичный случай. В run 307, 187, 164 и 214 найдены соответственно 9, 12, 8 и 22 уникальные пары `RequiredDigestFact → reply fragment`, где parent context непустой, а извлечённый `PublicationEvidence.text` отличается от своего raw `source_text`. Внутри того же frozen input PUBLISH-support родительского сообщения нашёлся только для 3/9, 2/12, 4/8 и 6/22 таких пар. Это индикатор риска, не автоматический вердикт: часть отличий может быть допустимым раскрытием короткого ответа с контекстом. В ручной сверке run 214 тезис «на Крылова сегодня света не ждут» был привязан к ответу «А не говорили когда ждать?», хотя текст исходного сообщения находился в родительском фрагменте; для одной линии в Колонии район указан только в родительском вопросе. Поэтому при исправлении нужно различать контекст, который уточняет референт, и первичный support самого события.

Сам binder тоже пока ненадёжен как измеритель: на run 307 он включил неизвестный ID в `uncovered_fact_ids` и назвал непокрытым известный факт про Военный городок, хотя дайджест сообщает об отключении там. На run 187 он не засчитал фразу про один доступный пункт выдачи на Троллейбусной, 22, хотя она есть в черновике; при этом текст неоправданно уточнил пол автора сообщения («одной горожанке» вместо нейтрального «пользователь»). Простой список support IDs на весь абзац не выражает связь конкретного факта с конкретным источником. Следующий контракт binder должен размечать каждую пару `claim span → fact ID → support ID`, а код — отдельно валидировать, что каждый ID принадлежит плану, каждый support допустим именно для этого fact ID, а каждый RequiredDigestFact либо покрыт, либо явно и корректно перечислен как непокрытый.

Архитектурный вывод: свободная композиция помогает читать текст, но сначала нужно исправить provenance в sealed Event-First material и добавить структурную проверку связей. Иначе repair-модель получает неверный ledger и может лишь аккуратно воспроизвести ошибочную привязку. Это выявление первопричины; production defaults не меняются, а дальнейший эксперимент должен использовать исправленный source ledger до настройки редакторского цикла.

В `scripts/digest_evaluation/binding_audit.py` добавлена только offline-проверка структуры нового контракта `абзац → fact ID → собственные support IDs`: она отклоняет неизвестные IDs, чужую привязку support к fact, неточные текстовые диапазоны и факты, не отмеченные ни покрытыми, ни непокрытыми. Пять целевых тестов прошли. Это не семантический verifier и не включено в production.

#### Проверка per-fact контракта на holdout run 187

Новый binder получил исходный черновик, 24 `RequiredDigestFacts`, первичные `source_text` отдельно от машинно извлечённых заметок и контекст ответов с явной пометкой `background_only_not_citable`. Поэтому список неподдержанных фрагментов неполон и целиком не проверялся.

В завершённой части ответа были 22 привязки: 10 `fully_supported`, 11 `partially_supported` и 1 `unsupported`; один факт повторялся в двух абзацах. Binder перечислил один непокрытый факт, но три других не связал вообще, а частичные/неподдержанные привязки не перечислил как непокрытые. Структурная проверка извлечённой части нашла 0 неизвестных fact IDs, 0 неизвестных support IDs и 0 чужих связей fact → support, но 13 обязательных фактов остались неучтёнными как полностью покрытые либо явно непокрытые. Значит, контракт помогает проверять точные связи ID, но этот ответ невалиден как замкнутый ledger покрытия и не доказывает семантическую поддержку.

На том же окне текущий дайджест занимает 4 113 кодовых точек (4 125 UTF-16 единиц), то есть превышает Telegram-лимит 4 096; в нём также дважды выведен заголовок, а слабые рубрики раздувают текст. Сокращённый текст перспективен как литературная форма, но этот holdout не проходит доказательную проверку.

Следующий шаг — исправлять владельца факта и источник в Event-First ledger до дальнейшей настройки writer/editor: каждый support должен оставаться тем фрагментом, который непосредственно сообщает факт; контекст родителя помогает понять ответ, но сам ответ не становится доказательством содержания родителя. Это должно исправляться локально для ошибочно извлечённого факта, без требования второго источника и без подавления остальных полезных одиночных сообщений. После этого нужна новая зафиксированная holdout-сверка, а не повторная настройка на тех же окнах.

### Исправление владения источником в reply-контексте, 06.10.2026

Проверка кода подтвердила путь утечки в Event Triage: prompt показывал текст родителя внутри строки дочернего фрагмента, а `story_frag_texts` сохранял ответ вместе с `in_reply_to`. Эта же склеенная строка затем использовалась как первичный текст в `normalize_service_state_evidence`, поэтому отдельное утверждение родителя могло пройти проверку как будто его содержал ответ.

Исправление разделяет первичный текст фрагмента и контекст родителя как на входе Gate, так и при проверке service state. System prompts Gate и Event Analysis явно требуют указывать только фрагменты, чьи собственные тексты подтверждают фактические части утверждения. Проверка сохраняет короткий ответ на явный вопрос (`«Да, минут десять назад»`) как точный `community_report` с PUBLISH, но без заимствованного текста и без неподтверждённого service state. Независимый факт из родителя, не подтверждённый ответом, переводится в CONTEXT. Версии Gate/analysis повышены, чтобы новые прогоны использовали обновлённые правила.

Регрессионные тесты покрывают разделение prompt-контекста, короткий прямой ответ, parent-only service claim и обычный прямой service report. Это узкая проверка правил привязки; она не является полной семантической проверкой всех типов `community_report` и не заменяет новое закрытое сравнение дайджестов.

### Привязка масштаба сообщения к конкретной услуге, 06.10.2026

### 2026-10-07 — порядок абзацев для насыщенной темы электричества

Писатель получал 15+ фактов об электричестве одной группой и складывал их в перечень адресов.
